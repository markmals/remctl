### AREA: Python private_call IPC MECHANISM (remctl-private ReminderKit helper)

**Summary:** remctl talks to its private ReminderKit layer through an out-of-process helper binary named `remctl-private`, compiled from Objective-C (`remctl-private.m`) against the PRIVATE `ReminderKit` framework. The IPC is a one-shot subprocess-per-call model: Python `subprocess.run([PRIVATE_PATH], input=json.dumps(data), text=True, timeout=30)` writes a single JSON object to the helper's stdin; the helper reads stdin to EOF, parses one JSON dict (max 1 MiB), performs exactly one action keyed by the `"action"` field, prints exactly one JSON line to stdout, and exits. There is NO argv-based dispatch and NO persistent daemon — every call spawns a fresh process. The response envelope on success is `{"status": <"created"|"updated"|"deleted">, "action": <echoed action>, ...action-specific fields}`; on error the helper prints `{"status":"error","message":<msg>}` and exits 1. Python's `private_call()` is lenient: it returns the parsed payload whenever stdout is a JSON dict, regardless of returncode (unlike `bridge_call()` which requires returncode==0). Callers gate on `result.get("status") == <expected>`. Two retry layers exist: `private_create_list_call` (list creation, 3 attempts with DB re-read recovery) and `private_action`/`private_location_action` (idempotent reminder actions, 3 attempts), both keyed off the transient-error sentinel substring "communicate with a helper application". `bridge_call` is the SEPARATE public path to a different binary `remctl-bridge` (Swift/EventKit) and is not part of the private layer, though some private operations (location alarms) prefer the bridge when available.

**Key findings:**
- TRANSPORT: one-shot subprocess per call. `private_call_result(data, timeout=30)` runs `subprocess.run([str(PRIVATE_PATH)], input=json.dumps(data), capture_output=True, text=True, timeout=timeout)`. Request = single JSON OBJECT on stdin (UTF-8 text). Response = single JSON line on stdout. NOT argv; NOT a daemon. Helper reads stdin to EOF, rejects empty input ('No input on stdin') and input >1048576 bytes ('Input too large').
- RESPONSE ENVELOPE: success = `{"status": <"created"|"updated"|"deleted">, "action": <echoed action string>, ...action-specific keys (e.g. id, url, name)}`. Error = `{"status":"error","message":<NSString>}` written by `fail()` which then `exit(1)`. `output()` always appends a trailing newline. Success exit code is 0; only `fail()` exits 1.
- PARSING LENIENCY: `private_call(data)` returns `result['payload']` iff it `isinstance(...,dict)` — it does NOT check returncode (remctl:2096-2101). Contrast `bridge_call` (remctl:2050-2055) which requires `returncode == 0 AND isinstance(payload, dict)`. So a helper that exits 1 but still printed a JSON error dict is surfaced to the caller, who then branches on `status`.
- BINARY LOCATION: `PRIVATE_PATH = resolve_binary_path(__file__, 'remctl-private', 'REMCTL_PRIVATE_PATH')` (remctl:52). `resolve_binary_path` precedence (remctl_runtime.py:66-86): env var `REMCTL_PRIVATE_PATH` (expanduser) → `<script_dir>/remctl-private` → `<script_dir>/bin/remctl-private` → `~/bin/remctl-private` → `~/.local/bin/remctl-private` → `shutil.which('remctl-private')` → fallback `<script_dir>/remctl-private`. `current_private_path()` (remctl:7013) repeats: env override → existing PRIVATE_PATH.resolve() → which → PRIVATE_PATH.resolve().
- AVAILABILITY GATE: `private_available()` (remctl:2067) = `PRIVATE_PATH.exists() and (st_mode & 0o111)` (exists AND executable bit). `private_metadata_enabled(a)` (remctl:2060) = True iff arg namespace has `.private` or `.private_metadata` truthy. `require_private_metadata(a)` (remctl:2142) enforces BOTH: if not enabled → stderr `Error: private metadata writes require --private.` exit 1; then if not available → stderr `Error: remctl-private is unavailable. Reinstall or set REMCTL_PRIVATE_PATH.` exit 1.
- TRANSIENT-ERROR DETECTION: `private_helper_error_is_transient(result)` (remctl:2104) = result is dict AND `str(result.get('message'))` contains the substring `'communicate with a helper application'`. This is the ONLY transient sentinel; matched as a substring of the helper's error message.
- LIST-CREATE RETRY: `private_create_list_call(request, name, attempts=3)` (remctl:2111). Loop up to 3 attempts: call private_call; return immediately if `status=='created'`; return the result immediately if error is NOT transient. On transient error, re-read DB up to 4 times with `time.sleep(0.25)` each via `q_list_exact_name_count(open_db(), name)` — if the list now exists, return a RECOVERED dict = copy of result updated with `{status:'created', action:request['action'], name:name, verifiedAfterTransientError:True}`. Between attempts: `time.sleep(0.75 * (attempt+1))` backoff. Catches `RemindersDBUnavailable` to break the re-read loop.
- REMINDER-ACTION RETRY: `private_action(data)` (remctl:2568). `attempts = 3 if data['action'] in IDEMPOTENT_PRIVATE_ACTIONS else 1`, where `IDEMPOTENT_PRIVATE_ACTIONS = {'assign_section','set_flagged','set_urgent','set_early_reminder'}` (remctl:2560). Loop: call private_call; return if `status=='updated'`; break if non-transient OR last attempt; else `time.sleep(0.5)`. On final failure prints `Error: {message}` (message from result dict or literal `private helper failed`) and exit 1.
- LOCATION ACTION: `private_location_action(data)` (remctl:2585) PREFERS the bridge: if `bridge_available()`, it sends a REMAPPED `bridge_call` payload `{action:'update', id, locationTitle, latitude, longitude, radius, proximity:'leaving' if proximity==2 else 'arriving'}` and on success returns a synthesized `{status:'updated', action:'add_location_alarm', source:'eventkit_bridge', locationTitle}`. Only when the bridge is absent does it fall to `private_call`, with 3 attempts + up to 8× `location_alarm_exists` DB-verification polls (0.25s) on transient error, synthesizing `verifiedAfterTransientError:True`.
- ALLOWED ACTIONS (helper-side allowlist, remctl-private.m:655-678; unknown → fail 'Unknown action'): add_private_metadata, add_url_attachments, add_tags, add_subtasks, assign_section, add_section_and_assign, add_attachments, set_flagged, set_urgent, set_early_reminder, add_location_alarm, create_list, set_list_appearance, set_list_pinned, set_smart_list_pinned, categorize_grocery_items, create_smart_list, update_smart_list, delete_smart_list, create_template, apply_template, delete_template.

### AREA: PRIVATE ACTION INVENTORY (remctl-private / ReminderKit IPC contract)

**Summary:** The Python CLI talks to the private ReminderKit helper (`remctl-private`, a separate ObjC binary at PRIVATE_PATH) over a single stdin/stdout JSON IPC: `private_call(data)` JSON-encodes `data`, runs the binary with `subprocess.run(..., input=json.dumps(data))`, parses stdout JSON, and returns the dict (or None). All requests carry a string `"action"` key. The caller only ever inspects the response `"status"` string (and `"message"` on error) — it does NOT consume any other response field except for a handful (`subtasks[].id`, `id`/`name` on create paths, `message`). There are exactly 16 distinct private actions emitted by the Python: 13 invoked at runtime, plus the ObjC helper additionally implements `add_url_attachments`/`add_tags` which the Python never calls. Critically, a SECOND IPC channel (`bridge_call` → `remctl-bridge`, the Phase-2 EventKit binary) handles a disjoint action set (`create`, `update`, `complete`, `uncomplete`, `delete`, `flag`, `unflag`, `create_list`(public title path), `rename_list`, `delete_list`, `authorize`); these are NOT private actions and must not be confused with them. The deferred top-level `flag`/`unflag` commands route through AppleScript-then-bridge, NOT through `private_call`; the private `set_flagged` action is only used inside add/edit `--private` and for subtasks. Success status strings vary per action family: created ops expect `"created"`, delete ops `"deleted"`, everything else `"updated"`. Transient-error retry is driven by the exact message substring "communicate with a helper application".

**Key findings:**
- IPC mechanism: `private_call(data)` (remctl:2096) → `private_call_result` (remctl:2072) runs `subprocess.run([str(PRIVATE_PATH)], input=json.dumps(data), capture_output=True, text=True, timeout=30)`, JSON-parses stdout, returns the dict or None. PRIVATE_PATH resolves `remctl-private` / env `REMCTL_PRIVATE_PATH` (remctl:52). availability gate: `private_available()` checks file exists + executable bit; `require_private_metadata(a)` additionally enforces `--private`/`--private-metadata` opt-in and exits(1) if helper missing.
- EXACTLY 13 private actions are emitted by the Python at runtime. ID-less list/smartlist/template ops: create_list, set_list_appearance, set_list_pinned, set_smart_list_pinned, categorize_grocery_items, create_smart_list, update_smart_list, delete_smart_list, create_template, apply_template, delete_template. (That is 11 + 9 = 20 emit sites but several share action names; total DISTINCT private action keys = 19 emitted + 2 helper-only.)
- Success status strings are NOT uniform. create_list/create_smart_list/create_template/apply_template → `status == 'created'`. delete_smart_list/delete_template → `status == 'deleted'`. ALL reminder-scoped ops + set_list_appearance/set_list_pinned/set_smart_list_pinned/update_smart_list/categorize_grocery_items → `status == 'updated'`. Anything else (or None) is treated as failure: caller reads `result['message']` (default 'private helper failed'), prints `Error: <message>` to stderr, exits 1.
- Error envelope from helper: `{"status":"error","message":<str>}` with helper exit(1). `private_call` still returns the parsed dict (returncode is ignored by `private_call`; only `private_call_result` exposes returncode). Transient-error detection: `private_helper_error_is_transient(result)` returns True iff `message` contains the substring 'communicate with a helper application' (full string uses curly apostrophe: "Couldn’t communicate with a helper application.").
- Retry semantics differ by wrapper. `private_action(data)` (remctl:2568): 3 attempts ONLY for IDEMPOTENT_PRIVATE_ACTIONS = {assign_section, set_flagged, set_urgent, set_early_reminder} (0.5s sleep between), else 1 attempt; success requires status=='updated', else exits 1. `private_create_list_call(request, name)` (remctl:2111): up to 3 attempts, on transient error re-reads DB via `q_list_exact_name_count(open_db(), name)` up to 4×(0.25s); if list appeared, returns recovered dict `{status:'created', action, name, verifiedAfterTransientError:True}`; backoff 0.75*(attempt+1). `private_location_action(data)` (remctl:2585): if bridge available, routes to bridge_call with translated payload instead; else 3 attempts with location-existence verification (verifiedAfterTransientError).
- BRIDGE vs PRIVATE split (do not conflate): bridge_call → remctl-bridge (EventKit, Phase 2) handles create/update/complete/uncomplete/delete/flag/unflag and create_list(public title path)/rename_list/delete_list/authorize. The deferred top-level `flag`/`unflag` commands (cmd_flag remctl:5957, cmd_unflag remctl:5993) use AppleScript-first (`set flagged of r to true/false`) then bridge_call `{action:'flag'/'unflag', id:<ckid>}` expecting status 'flagged'/'unflagged' — they NEVER call private_call. The private `set_flagged` action only appears in apply_private_changes (add/edit --private) and apply_subtask_private_metadata.
- `private_location_action` bridge translation (remctl:2585): when bridge available, builds `{action:'update', id, locationTitle, latitude, longitude, radius, proximity}` where proximity int 2→'leaving' else 'arriving' (note: bridge uses string proximity; private uses int 1=enter/2=leave). Returns synthesized `{status:'updated', action:'add_location_alarm', source:'eventkit_bridge', locationTitle}`.
- Appearance payload helper `list_private_appearance_payload(a, include_public_color_names)` (remctl:2716) builds the shared key set merged into create_list/set_list_appearance/create_smart_list/update_smart_list: optional `name` (from --new-name), `color` (normalize_list_color; named colors only included when include_public_color_names=True OR value is hex), `symbol`(.strip()), `emoji`(.strip()), and grocery keys `shouldCategorizeGroceryItems`(bool)+`groceryLocaleID`(str, default 'en_US') or just `shouldCategorizeGroceryItems:false` for --standard.

### AREA: flag / unflag

**Summary:** cmd_flag (remctl:5957) and cmd_unflag (remctl:5993) toggle a reminder's REAL flagged state (the ZFLAGGED column). Both take a single positional int id (Z_PK) plus --json. They resolve pk→reminder via q_reminder(db, id) (same SQL as `done`), then attempt writes in an INVERTED order vs done/undone/delete: AppleScript FIRST (`set flagged of r to true/false` via osa_by_id_try, matched by `x-apple-reminder://<ZCKIDENTIFIER>`, 120s timeout), then EventKit bridge as a LOSSY fallback (`{"action":"flag"/"unflag","id":<ZCKIDENTIFIER>}`). AppleScript is primary precisely because EventKit/the bridge has no public flagged property — it approximates a flag with priority=1, which destroys the real ZPRIORITY value. In the Swift port, Phase 2's EventKitWriter does exactly this lossy priority-1 proxy (EventKitWriter.swift:164-168), and Phase 2 removed osascript, so the correct flag/unflag path is deferred to Phase 3's private ReminderKit layer. The private layer already exposes the exact action needed — `set_flagged` with payload {"action":"set_flagged","id":<ckid>,"flagged":<bool>} — used today by add/edit (remctl:2417, 3087). The Swift FlagCmd/Unflag are clean NotImplemented stubs (WriteCommands.swift:612-622). NOTE: the current Python flag/unflag do NOT call set_flagged; that private action is the intended replacement for the removed AppleScript path. The Phase-3 task is to re-implement flag/unflag in-process: resolve pk→ckid, call ReminderKitPrivate set_flagged (true for flag, false for unflag), and on failure fall through to the in-process EventKit priority-1 proxy, preserving the exact output/error strings and exit codes below.

**Key findings:**
- CLI surface: both `flag` and `unflag` take one positional `id` (type=int, the numeric Z_PK) and `--json` only. No -v, no --format. Argparse at remctl:7821-7822: `c=sub.add_parser('flag',...); c.add_argument('id', type=int); js(c)` and identical for unflag. Swift stubs already declare commandName flag/unflag + @OptionGroup JSONOptions (WriteCommands.swift:613-621).
- Resolution pk→reminder: `r = q_reminder(db, a.id)` (remctl:1281) — `SELECT {rem_cols} FROM ZREMCDREMINDER r LEFT JOIN ZREMCDBASELIST l ON r.ZLIST=l.Z_PK WHERE r.Z_PK=? AND r.ZMARKEDFORDELETION=0 AND r.ZACCOUNT IS NOT NULL`. The ckid for writes comes from `r['ZCKIDENTIFIER']` (a column in rem_cols). If row is None → not-found error. No second pk→ckid query; ckid is already on the row.
- Why it cannot be EventKit: EventKit has NO public `flagged` property. The bridge/EventKitWriter approximates a flag by setting priority=1 (and unflag by clearing priority 0 when currently 1) — confirmed in the Python comment at remctl:5964-5967 and in the Swift port EventKitWriter.swift:164-168. This is LOSSY: it overwrites the real ZPRIORITY. Only AppleScript `set flagged of r` (or the private ReminderKit `set_flagged`) touches the true ZFLAGGED column. Phase 2 removed the osascript path, so flag/unflag are deferred to the Phase-3 private layer.
- Write order is INVERTED vs done/undone/delete. AppleScript-FIRST: `rid = _rem_id(r)` = `x-apple-reminder://<ZCKIDENTIFIER>` (None when no ckid; remctl:5278). If `rid and osa_by_id_try(r['list_name'], rid, 'set flagged of r to true')` succeeds → print success + return. osa_by_id_try uses a 120s timeout (remctl:3766).
- Bridge fallback only runs if AppleScript failed AND `bridge_available() and r['ZCKIDENTIFIER']`. Payload `{'action':'flag','id':r['ZCKIDENTIFIER']}` (flag) / `{'action':'unflag','id':...}` (unflag). Accepts ONLY when `result.get('status')=='flagged'` / `=='unflagged'`. bridge_call returns parsed JSON only if returncode==0 and payload is a dict (remctl:2050-2055).
- Failure handling: if `not rid` (no stable identifier) → `_refuse_unsafe_title_fallback(r, 'flag it'/'unflag it', 'The reminder has no stable identifier')`. Otherwise (both paths failed) → `_refuse_unsafe_title_fallback(r, ..., 'Identifier-based writes failed')`. Both call sys.exit(1). There is NO title-based AppleScript fallback — it is explicitly refused (remctl:5296-5307).
- The private action that replaces the removed AppleScript path is `set_flagged`. Exact payload (from add/edit, remctl:2417-2421 and 3087-3091): `{'action':'set_flagged','id':<reminder_ckid>,'flagged':bool}`. `set_flagged` is in IDEMPOTENT_PRIVATE_ACTIONS (remctl:2562) → private_action retries up to 3x on transient 'communicate with a helper application' errors. Success is `result.get('status')=='updated'`. For Phase 3 flag→flagged:true, unflag→flagged:false.
- IPC envelope (Python external helper, to be folded in-process for Swift): request = `json.dumps(data)` written to remctl-private stdin; response = JSON object on stdout (remctl:2072-2101). private_call returns the parsed payload dict or None. require_private_metadata gates on `--private` opt-in + helper availability (remctl:2142). ### AREA: PRIVATE FLAGS stubbed in add/edit/list-create (Phase-3 ReminderKit private-metadata layer)

**Summary:** The Python remctl drives all "private" writes through a single IPC chokepoint: `private_call(data)` (remctl:2096) JSON-encodes a dict to stdin of the external `remctl-private` ObjC helper (remctl-private.m) and parses the JSON dict on stdout. Every private flag on add/edit/list-create is just a builder that produces one of a fixed set of `{"action": ...}` payloads, dispatched per-reminder by `apply_private_changes` (remctl:3003), per-list by `apply_private_list_appearance` / `list_private_appearance_payload` (remctl:2716/2746), or at list creation by an inline `create_list` request (remctl:6098). The helper returns `{"status":"updated"|"created", "action":..., ...detail keys}` on success or `{"status":"error","message":...}` on failure; the Python `private_action` wrapper retries idempotent actions on transient "communicate with a helper application" errors and exits 1 on any other failure. The Swift port has folded the helper in-process as the `ReminderKitPrivate` ObjC target (currently only an `RKPProbe()` stub), and every private flag in add/edit/list-create currently throws `WriteError("<flag> requires the private metadata layer (Phase 3); not yet implemented.")` via a `phase3(_:)` helper. Phase 3 must replace those stub throws with builders that produce the exact same action payloads and feed them to an in-process equivalent of `private_call`. Note two PARITY DIVERGENCES the Swift stubs introduced that Phase 3 must resolve: in Python `--flag` (add) and `--tags`/`--url` (add/edit) are PUBLIC paths when `--private` is absent (inline #hashtag title append, notes-append, EventKit flagged), but the Swift stubs throw phase3 unconditionally for `--flag` and `--tags`; and the Swift port dropped the `--private` opt-in flag entirely.

### AREA: ReminderKit framework + entitlements/risk (Phase-3 in-process feasibility)

**Summary:** Phase 3 folds Apple's PRIVATE ReminderKit.framework in-process via the Obj-C `ReminderKitPrivate` target (a near-verbatim reuse of `remctl-private.m`, 1,430 lines). The framework is at `/System/Library/PrivateFrameworks/ReminderKit.framework`; it is linked with `-F /System/Library/PrivateFrameworks -framework ReminderKit` (already wired in Package.swift). I empirically verified on this machine (macOS 26.5, build 25F71) that an ad-hoc/linker-signed binary AND a hardened-runtime-signed binary, BOTH with ZERO entitlements, successfully resolve `REMStore` via the dyld shared cache and instantiate it (`[REMStore new]` returns non-nil). So framework LINK + LOAD + class resolution require no special entitlements — the Phase-0 `RKPProbe()` proves this and the design is sound for a SOURCE-BUILT, locally/ad-hoc-signed binary. The distribution risk is NOT linkage; it is (1) Apple will not NOTARIZE a binary that links a /System/Library/PrivateFrameworks framework, and (2) actual CloudKit-backed SAVES go through remindd and MAY require the `group.com.apple.reminders` app-group + private TCC entitlements that Reminders.app holds and a third-party binary cannot legitimately claim. Crucially, the planned Homebrew distribution is a SOURCE build (`swift build -c release`, `depends_on xcode: :build`, no codesign/notarize step) which entirely sidesteps the notarization blocker — the user compiles locally, getting an ad-hoc signature, exactly like the current Python `install.sh` path. The design spec already enumerates these risks (lines 104-107) and the owner has ACCEPTED the in-process approach. Recommendation: keep in-process as planned for the source-build Homebrew path; the only thing that would block distribution is a future pivot to shipping pre-built/notarized bottles.

Re-signed it with `codesign -f -s - --options runtime` (hardened runtime, the notarization prerequisite) WITH NO ENTITLEMENTS — still loads and instantiates. So no `com.apple.developer.reminders`, no `reminders-kit`, no app-group entitlement is needed to LINK or to reach the API surface. (The Phase-0 PrivateLinkTests `RKPProbe()` asserting 'reminderkit-ok' corroborates this.)
- ENTITLEMENTS — the REAL gate is at the SAVE/CloudKit layer, NOT link time. Reminders.app (`/System/Applications/Reminders.app`) holds Apple-private entitlements a third party cannot self-grant: `com.apple.security.application-groups: group.com.apple.reminders`, `com.apple.private.security.restricted-application-groups: group.com.apple.reminders`, `com.apple.private.tcc.allow: [kTCCServiceReminders, kTCCServiceAddressBook]`, `com.apple.developer.icloud-container-identifiers: com.apple.reminders`, `com.apple.private.remindd`, `com.apple.private.cloudkit.masquerade`. REMStore/REMSaveRequest operate on the SHARED Reminders store via remindd over XPC; the existing Python helper proves SAVES work WITHOUT these entitlements (it is compiled ad-hoc with no entitlements and the docs/architecture claim verified private writes materialize), because writes go through the user's own granted Reminders TCC permission + the shared CoreData/CloudKit container that remindd owns — not through the calling binary's entitlements. This is the load-bearing assumption to preserve: the binary needs the standard Reminders TCC grant (already obtained via EventKit `requestFullAccessToReminders`), nothing more.
- CODE-SIGNING / NOTARIZATION — the one concrete distribution blocker, but the planned path avoids it. Apple's notary service REJECTS binaries that link /System/Library/PrivateFrameworks (`-F /System/Library/PrivateFrameworks` linkage is flagged as use of private API). The planned Homebrew formula (design §7, lines 114-135) does a SOURCE build: `system 'swift','build','--disable-sandbox','-c','release'` with `depends_on xcode: :build`, then `bin.install`. There is NO codesign --options runtime and NO notarization step. The resulting binary is ad-hoc/linker-signed locally on the user's machine — identical signing posture to the current Python `install.sh` (`clang ... -framework ReminderKit` with NO codesign step). Ad-hoc-signed local binaries are NOT subject to notarization/Gatekeeper quarantine when built locally via Homebrew, so private-framework linkage does not block this distribution model.
- TCC / PERMISSION PROMPTS — unchanged from EventKit path; no NEW prompt from ReminderKit. The binary already triggers the standard `kTCCServiceReminders` prompt via EventKit `requestFullAccessToReminders` (remctl-bridge.swift requestAccess). ReminderKit/REMStore piggyback on that same Reminders TCC grant; instantiating REMStore needed no separate prompt in my probe. Image attachments read local files (Full Disk Access / user-selected file scope may matter for arbitrary paths, but the helper only reads explicitly-passed image paths). Folding in-process means the SINGLE `remctl` binary's TCC identity (its cdhash/bundle-id-less ad-hoc identity) is what TCC records — a change from today where 3 separate helper binaries each had their own identity; re-grant may be required on upgrade, and an ad-hoc identity's TCC grant is keyed on cdhash so EVERY rebuild/version could re-prompt for Reminders access unless a stable signing identity is used.
- macOS-VERSION FRAGILITY — high and tracking tightly to the OS. ReminderKit.framework Info.plist: `CFBundleVersion=3976`, `LSMinimumSystemVersion=26.5`, `DTPlatformVersion=26.5`. The framework version moves with every macOS point release. The helper is defensive (`respondsToSelector:` guards before nearly every private selector, `@try/@catch` around save, `setValue:forKey:` for `minimumSupportedVersion`/`effectiveMinimumSupportedVersion=20220430`), and contains dated empirical workarounds (e.g. line 466: 'ReminderKit rejects cyan as a symbolic private color on current macOS' => substitutes #5AC8FA; smart-list supported-version=20220430 required or filters render as zero). Selector signatures or the `x-apple-reminderkit://REMCD*/<ckid>` URL scheme could change across major macOS versions, silently breaking private writes. In-process this means a framework ABI change is a build/runtime fault inside the main CLI process (mitigated by @try/@catch -> NSError, per design §6 line 104).
- PRIVATE CLASS/SELECTOR SURFACE (exhaustive, from remctl-private.m headers): Classes — REMObjectID, REMStore, REMSaveRequest, REMAccount, REMAccountChangeItem, REMAccountCapabilities, REMSmartList, REMSmartListChangeItem, REMSmartListCustomContextChangeItem, REMTemplate, REMTemplateChangeItem, REMTemplateConfiguration, REMReminder, REMReminderChangeItem, REMReminderDueDateDeltaAlertContextChangeItem, REMDueDateDeltaInterval, REMReminderAttachmentContextChangeItem, REMReminderHashtagContextChangeItem, REMReminderFlaggedContextChangeItem, REMReminderUrgentAlarmContextChangeItem, REMListChangeItem, REMListGroceryContextChangeItem, REMListAppearanceContextChangeItem, REMListBadge, REMColor, REMListSectionChangeItem, REMListSectionContextChangeItem, REMMembership, REMMemberships, REMStructuredLocation, REMAlarmLocationTrigger, REMAlarm. - IPC/INVOCATION MODEL TODAY vs PHASE 3: Today Python invokes the external `remctl-private` subprocess (remctl:2072 `private_call_result` => `subprocess.run([PRIVATE_PATH], input=json.dumps(data), text=True, timeout=30)`), parses one JSON line from stdout. Phase 3 RETIRES `REMCTL_PRIVATE_PATH` (design §97) and replaces the subprocess with a direct Swift facade -> ObjC ReminderKitPrivate call. The 22 actions and their exact stdin/stdout JSON envelopes (below) define the facade's API contract — they must be preserved 1:1 for JSON parity, but the subprocess hop, 30s timeout, and the transient 'communicate with a helper application' retry logic (remctl:2104-2139) all collapse in-process. The transient-retry was specifically for XPC-to-remindd flakiness during list creation; in-process the same remindd XPC flakiness can still occur so the retry/re-read logic should be ported.

**Risks/unknowns:**
- UNVERIFIED (intentionally — must not mutate the live store): I confirmed link/load/instantiate of REMStore without entitlements, but I did NOT execute an actual saveSynchronouslyWithError: (would write to the user's real Reminders). The assumption that SAVES succeed without app-group/private-TCC entitlements rests on the existing ad-hoc-signed Python helper working (per docs/architecture.md:57 'verified private writes include...') and on saves routing through remindd+the user's Reminders TCC grant rather than the caller's entitlements. This is the single highest-leverage unknown for Phase 3 — validate early with a throwaway list create/delete on the Swift binary before building out all 22 actions.
- TCC IDENTITY ON UPGRADE: TCC keys Reminders access on the binary's code signature (cdhash for ad-hoc). A locally-Homebrew-source-built ad-hoc binary gets a fresh cdhash on every version/rebuild, so users may be re-prompted for Reminders access (and Full Disk Access for the SQLite reads) on each upgrade. The current 3-helper Python design has the same issue per-helper. Consider a stable ad-hoc identity or documenting the re-grant; not a blocker but a UX regression risk.
- NOTARIZATION HARD BLOCK if distribution ever pivots to PRE-BUILT BOTTLES or a signed/notarized DMG: Apple notary rejects -F /System/Library/PrivateFrameworks linkage. The current source-build formula avoids this, but Homebrew `test-bot` produces bottles (design §7 line 112 mentions bottle building on the tap) — if those bottles are pre-compiled and shipped, the binary must still be ad-hoc/locally-acceptable; if any future step adds `codesign --options runtime` + notarization it WILL fail. Keep the formula a pure source build.
- PRIVATE-API DRIFT across macOS major versions: selector renames, the 20220430 supported-version magic number, the cyan-color rejection workaround, and the x-apple-reminderkit URL scheme are all empirically-derived and version-sensitive. In-process, a fault is caught by @try/@catch -> NSError (design mitigation), but a SILENT semantic change (e.g. filterData writing zero filters) won't throw — only the live smart-list materialization tests (scripts/live_private_matrix.py, to be ported) catch these. Phase 3 should port that live matrix as the regression guard.
- EventKit + ReminderKit in ONE process/store session (design §6 line 105, Medium): two stacks (EKEventStore + REMStore) over the same CloudKit-backed CoreData container in one process can race on saves. The current design uses SEPARATE subprocesses (bridge vs private) so they never coexist; folding in-process removes that isolation. Mitigation per spec: serialize saves, re-fetch after write. For rich subtasks specifically the current flow is two-step (private creates child + private metadata, THEN bridge applies public child fields) — in-process this becomes two saves on possibly-different store objects for the same child; ordering/refetch must be preserved.
- App Store distribution is impossible (private framework) — but RemCTL targets Homebrew only, so out of scope. Note for completeness in case future direction changes.
- remctl-private.m is 1430 lines and I read it fully; the ReminderKitPrivate scaffold currently contains ONLY RKPProbe() (10 lines) — the entire write surface still has to be ported in. The scaffold's .m has no real ObjC class decls yet; Phase 3 must paste in the @interface forward decls + all 22 action handlers (or expose a narrower facade).
